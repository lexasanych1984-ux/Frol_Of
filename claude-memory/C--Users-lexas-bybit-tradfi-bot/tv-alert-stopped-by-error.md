TradingView может **сам выключить strategy-алерт**, и `alert_list` (internal_api) отдаёт лишь
`active: false` — БЕЗ причины. Причина есть только в DOM панели «Оповещения»:
`[data-name="alert-item-status"]` внутри строки `[class*="itemBody-"]`.

**Причина найдена и вылечена 30.07.2026.** В SMC-скрипте ветки `if bosUp` / `if bosDn`
обращаются к серии по ПЕРЕМЕННОМУ индексу (`low[i]`, `high[i+2]`, `close[i]` — до 20 баров
назад), а `max_bars_back` не был задан: Pine выделяет буфер по обращениям, увиденным на первых
барах, глубокие спрятаны за условием BOS → при первом BOS расчёт падает. Профиль отказа сходится
полностью (на графике считается, на сервере алерта падает; GBPJPY выжил, EURUSD нет). Лечение —
`max_bars_back=100` в `strategy()` (скрипт в облаке TV стал v24, логика не менялась) и
пересоздание всех трёх SMC-алертов на v24, т.к. алерт приколот к версии на момент создания:
EURUSD 15m `5261914051`, GBPJPY 15m `5261914152`, GBPJPY 1H `5261914285`. Копия исходника —
`C:\Users\lexas\tv-strategies\fx-indices\smc-2koleno-v24-alerts.pine`.

Различай два статуса — они означают разное:
* **«Остановлено — Сработало»** — норма для drawing-алертов с `frequency: on_first_fire`
  (отстрелялся один раз и погас).
* **«Остановлено — Ошибка расчёта»** — ошибка выполнения Pine на стороне TV. Так 29.07.2026
  в 21:53 МСК умер алерт 5198786079 (SMC EURUSD 15m, pine 89bffcd5…, v23) ровно на баре, где
  отдавал ВЫХОД. Тот же скрипт на GBPJPY 15m/1H продолжал работать — значит дело в данных
  символа, а не в скрипте целиком. Перезапуск не устраняет причину: может лечь снова.

Перезапуск строки без мышки (панель «Оповещения» должна быть открыта — таб
`[class*="segmentedControlBase"]` с текстом «Оповещения»): найти строку по имени и
кликнуть `[data-name="alert-restart-button"]` через `ui_evaluate`, рассылая
pointerdown/mousedown/pointerup/mouseup/click. MCP-инструментов включения алерта нет —
только create/list/delete, а пересоздавать strategy-алерт с десятками pine-инпутов опасно.

**Переименование алерта в диалоге TradingView приклеивает имя к ТЕЛУ сообщения**: у CRT
30.07.2026 «{{strategy.order.alert_message}}» стало «CRT GER40 1H (webhook)
{{strategy.order.alert_message}}». Парсер бота ищет ключевые слова в любом месте строки, так
что этот префикс безвреден — проверено на всех 10 сообщениях, которые может прислать CRT v25
(вход стопом и лимитом в обе стороны, 3 выхода, БУ, 2 отмены): разбор идентичен, включая тип
ордера limit/stop. **Но в имена алертов нельзя вставлять `ВЫХОД`, `ОТМЕНА`, `LONG`, `SHORT`,
`БУ`** — алерт с именем «SMC ВЫХОД EURUSD» превратил бы каждый вход в команду на выход.
С 30.07.2026 сторож сверяет и текст сообщения (поле `message` в эталоне), так что подмена тела
всплывает за час. API переименования нет вообще (проверено 12 эндпоинтов) — только UI-диалог.

**Алерт приколот к версии скрипта на момент создания** — правка скрипта сама по себе в бой НЕ
попадает, нужно пересоздание (`scripts/recreate-alert-with-webhook.cjs --pine-version=`).
Отсюда же выглядело расхождение у Asia Sweep: скрипт сохранён как **v22**, алерты бегут **v20**.
Проверено 30.07.2026 — исходники v20 и v22 **байт-в-байт идентичны** (34597 знаков, 652 строки,
ноль различающихся строк): TradingView бампает версию на каждом сохранении, даже пустом.
Пересоздавать алерты Asia не нужно. Исходники любой версии тянутся без редактора:
`GET https://pine-facade.tradingview.com/pine-facade/get/USER;<pine_id>/<версия>` (поле `source`,
синхронный XHR из контекста страницы) — это безопаснее, чем открывать скрипт в Pine-редакторе,
где имя и содержимое разъезжаются и Save пишет код в чужой скрипт.

Проверены на ту же мину (обращение к серии по переменному индексу) и **чисты**: CRT v25 и
Asia v20 — динамических индексов нет вообще, обращения к массивам защищены (`if idx >= 2`,
`if bullClStart >= 0`).

Конфиг-watchdog ([[monitoring-health]]) это расхождение поймал корректно. Раньше задача
`TV-Watchdog-Configs` стояла на два прогона в день (09:15 и 21:15), поэтому смерть алерта в
21:53 всплыла только утром — слепое окно ~12 часов. **30.07.2026 переведена на почасовой
прогон**: ежедневный триггер 09:15 + повтор каждый час 14 ч (последний ~23:15), плюс снят
запрет запуска на батарее (по умолчанию Планировщик глушил задачу на ноутбуке). Расписание
зашито в `install-watchdog-task.ps1` (параметры `-Start/-IntervalMinutes/-DurationHours`),
так что переустановка его не откатит.
