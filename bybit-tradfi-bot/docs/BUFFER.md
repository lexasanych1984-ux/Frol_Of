# Облачный буфер сигналов (store-and-forward)

**Зачем.** Раньше бот видел алерт TradingView **только пока он запущен и TV жив**:
живой поток идёт через CDP-чтение push-канала `pricealerts`, а истории нет (endpoint
`/list_fires` удалён на стороне TV). Перезапуск TV, ребут/выключенный ПК, падение
процесса — **сигнал за это время терялся навсегда**. Это был главный единый узел
отказа форвард-теста.

**Решение.** TradingView-алерты дополнительно постят тело в облачный приёмник
(**Cloudflare Worker + D1**, каталог `cloud/`); он буферизует ≥7 дней. Бот
**опрашивает** облако (pull, каждые ~12 с) и добирает всё, что пришло за простой.
Никаких входящих портов на домашнем ПК.

```
TradingView (серверный алерт срабатывает)
   ├─(быстро)  push pricealerts ─► CDP :9222 ──────────┐
   └─(надёжно) web_hook POST ─► Cloudflare Worker ─► D1 (буфер 7 дней)
                                                        │ GET /pull?after=<id>
                                       WebhookPullSource ◄┘ (pull каждые ~12 с)
                                          │
   CompositeSource (слияние очередей) ────┘
        Engine.handle_raw(raw, received_ts, source, ext_id)
        дедуп по хэшу содержимого ─► гейт свежести (max_age) ─► риск ─► MT5
```

CDP остаётся **быстрым** каналом, webhook — **надёжным** резервом. Между ними дедуп по
хэшу содержимого (`Signal.dedup_key`) в пределах `dedup_window_sec` (900 с).

## Защита протухших сигналов (max_age)

После простоя бот добирает сигналы из буфера — вход по **устаревшей цене** исполнять
нельзя. Возраст сигнала = `сейчас − received_ts` (метка времени: `ts` из облака или
`fire_time` из CDP).

| Тип сигнала | Лимит (дефолт) | Поведение при превышении |
|-------------|----------------|--------------------------|
| ВХОД | `entry_max_age_sec` = **600 с (10 мин)** | НЕ исполняется, Telegram «⏳ Пропущен по возрасту», помечается seen |
| БУ / ВЫХОД | `manage_max_age_sec` = **21600 с (6 ч)** | Исполняется (позиция уже открыта) |

Настройка — `config.yaml → signal_freshness` (в т.ч. `per_strategy` override) и
`.env` (`WEBHOOK_ENTRY_MAX_AGE_SEC`, `WEBHOOK_MANAGE_MAX_AGE_SEC`). Если `received_ts`
неизвестен (напр. локальный http-тест) — сигнал считается свежим (живой CDP всегда свеж).

## Курсор и дедуп

- Бот хранит курсор `after=<id>` в `state.db` (таблица `meta`, ключ `webhook_cursor`).
  Первый старт: курсор = текущий `max_id` (история буфера **не** переигрывается).
  Рестарт: курсор из State → добор именно пропущенного за простой.
- Облако дедуплицирует ретраи TradingView по хэшу `(тело + минута)` — повторный POST
  того же тела в пределах 2 мин не создаёт вторую запись.
- Один и тот же fire по обоим каналам (CDP мгновенно + webhook ≤15 с спустя) — второй
  отбрасывается движком по хэшу содержимого в окне `dedup_window_sec`.

## Настройка

1. Развернуть приёмник — **`cloud/README.md`** (Cloudflare Worker + D1, ~10 мин, $0).
2. В `.env`: `WEBHOOK_PULL_URL`, `WEBHOOK_TOKEN` (длинный случайный, тот же в облаке).
   Прочие `WEBHOOK_*` — опциональны (дефолты разумны).
3. Пересоздать 6 алертов TradingView с полем webhook — см. раздел ниже.
4. Проверить цепочку: `python run.py webhook-selftest`.

Webhook включается, только если заданы и URL, и токен. Иначе бот работает как раньше
(один CDP-канал) и пишет об этом в лог.

## Пересоздание алертов TradingView

Поле webhook нельзя добавить, не пересоздав алерт. Пуши в приложение при этом
**сохраняются** (`mobile_push:true`). Делается **только через REST-рецепт** (не вручную)
generic-скриптом `tradingview-mcp/scripts/recreate-alert-with-webhook.cjs`, который
берёт **живые** inputs алерта (чтобы не изменить параметры стратегии) и лишь
проставляет `web_hook`.

⚠️ Существующие шаблоны `create-smc-alert.cjs`/`create-crt-alert.cjs` содержат
**устаревшие захардкоженные inputs** — по ним пересоздавать НЕЛЬЗЯ.

Пошаговый план (6 алертов, по одному с подтверждением) + контрольный прогон
config-watchdog по эталонам (`node watchdog\watchdog.mjs --baseline` → `--dry`) —
в approved-плане проекта. У пересозданных алертов **новые `alert_id`**, поэтому эталон
watchdog надо пересобрать (`--baseline`), затем чистый прогон подтверждает 6/6.

**Предпосылка:** тариф TradingView с поддержкой webhook (Essential/Plus/Premium).

## Наблюдение (health)

Webhook-канал встроен в heartbeat 5-й проверкой **«Резервный webhook-буфер»** (принцип
«молчание = авария»). Критерий — был ли недавно **успешный опрос** (пустой ответ =
норма, буфер часто пуст), а не «пришли ли сигналы». Нет успешного опроса дольше
`WEBHOOK_STALE_SEC` (90 с) → `🔴 АВАРИЯ` в Telegram. В суточной сводке проверки
становятся `5/5`.

## Приёмка

- **Симуляция «бот выключен 30 минут»** — `tests/test_acceptance_buffer.py`: за простой
  в буфер пришли вход (30 мин назад) и БУ (5 мин назад); после старта вход **пропущен по
  возрасту** с уведомлением, БУ **исполнен**, курсор продвинут.
- Юнит-тесты: `tests/test_freshness.py` (max_age вход/управление, per-strategy, дедуп
  между каналами), `tests/test_webhook_source.py` (порядок доставки, персист/инициализация
  курсора, health).
- Живая цепочка: `python run.py webhook-selftest` (round-trip POST /hook → GET /pull).
